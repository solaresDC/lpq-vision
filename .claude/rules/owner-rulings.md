## How the build runs (standing rules)
- A section arrives in parts, one part per message (Claude Code's input limit is about 50,000
  characters). Execute NOTHING until the last part, the one that ends with the deviations line.
- An exact edit quotes the current text it replaces. If it does not match: STOP that edit, apply the
  rest, run the checks, HOLD the commit and report the current text. A STOP is the right move, never a
  guess.
- Exact edits are applied with your Edit tool and whole files are written with your Write tool (a
  script passed through the shell mangled backslashes in the handover).
- Report every command's output (long build progress and per-request noise may be trimmed: say so).
  Any action outside the block is a deviation: list it in the deviations report.
- Shell: the listed commands run in Git Bash with MSYS_NO_PATHCONV=1 (running them from PowerShell is
  not a deviation). Always `-f compose.mac.yaml`. A bare sleep is blocked in your shell: use a timed
  loop and list it as a deviation. docker cp and docker exec with Windows paths work from Git Bash
  (with MSYS_NO_PATHCONV=1) and from PowerShell.
- Files: LF, a final newline, UTF-8 without BOM; check with `git ls-files --eol`. JavaScript syntax is
  checked with `node --check` on .mjs copies (node reads a .js file as CommonJS).
- Blocks never contain the dollar sign (the chat's renderer eats it): a new regex ends with \Z instead,
  a line that must keep one is copied from git, and every block scans its added lines with chr(36). A file that
  needs the sign itself (a shell script, 3.17) travels with each one written as @DOLLAR@, and a listed one-liner
  turns them back into chr(36) before the fingerprints.
- Blocks carry no backslash-u escape and no decomposed character (3.13.1's lesson): your tool calls turn
  a backslash-u escape into the character itself, and your Edit tool composes characters (NFC) before
  matching. Code that needs such a character builds it with chr().
- Where files go: throwaway files (the .mjs copies, temporary output) in your session scratchpad; a
  file a later step reads again (a snapshot) in `claude-autogenerated-docs/scratch/`; a throwaway
  check script in `photos/_smoke/`, run inside the fastapi container. `claude-autogenerated-docs/`
  and `photos/` are git-ignored.
- Checks make their own test accounts (random passwords, never printed), test dishes and test sites,
  and delete them in a finally block; a check that writes config.yaml keeps its exact bytes and writes
  them back. A check scans its own output for the passwords it made and for the env secrets (the bot
  token, the chat id, the API key) and fails if one appears; Telegram senders are replaced by a stub
  that raises (or records, when the check tests a send); every SQL statement's placeholders are verified
  against the keys passed (an AST check). A check never touches the laptop's real cuarto row (born by
  set_password in 3.5).
- Smoke tests use photos/smoke_diet.jpg (the 1600 px light copy), never a full-size original (Fase 2
  HQ ruling 2.15).
- Commits: the section's exact title as the message, plus the same Co-Authored-By trailer the earlier
  commits carry. NEVER push: the owner pushes from PowerShell (Tailscale off for the push only).
- Laptop test edits to config.yaml and textos.yaml are reverted before each commit (CLAUDE.md rule 19).
- The laptop's bot stays STOPPED: one poller per token (the server's bot is the live one). A live bot
  test on the laptop sits between a listed stop of the server's bot and its start again (the owner
  runs both in the section's ✋). Never press Start on the whole project in Docker Desktop (it starts
  the bot too).
- If Docker Desktop is closed, you may open it yourself (the 3.2 and 3.10.2 precedent): it brings back
  only the containers that were running. Never press Start on the whole project, and confirm the bot
  is still stopped.
- The menu version never rewinds: a bump on a REAL dish is permanent on that database, so only a block
  bumps one. A check bumps only its own test dishes and deletes them at the end (MAX then returns to
  its value).
- `/log` saves the session log to claude-autogenerated-docs/sessions/. When a conversation runs out of
  space, a new one starts from this file, CLAUDE.md, the newest logs and git.

### 3.16 (built in Section 3.16): the butler
- The butler (el mayordomo; SPEC 1.7 and 3.16's promise list): butler/lpq_butler.py (standard library only) and
  butler/lpq-butler.service. A service of the server's host only, installed in 3.18; never a service on the laptop.
  Built defaults (HQ's standard choices; the owner may change any of them):
  - The mailbox: /run/lpq-butler/butler.sock, root-only; its folder is bind-mounted into fastapi READ-ONLY and nowhere
    else (the compose ADD, in both compose files, with the bot's logs volume): fastapi can talk to the butler, never
    touch its files. One line per connection and one answer: "ok <id>" (the UTC time plus 4 hex; the bitácora row of
    the act carries it, and so does the butler's log) or "rechazado: <motivo>", in words the room shows as they are.
    A connection that sends nothing is the probe: closed, never logged. A line must arrive whole within 2 s.
  - Each line runs ONE exact command, never through a shell, in /opt/lpq_vision with a fixed clean environment:
    reboot = `/usr/bin/systemctl reboot`; scale worker N = `/usr/bin/docker compose -f compose.mac.yaml up -d
    --no-deps --no-recreate --no-build --scale worker=N worker`; restart S = `/usr/bin/docker compose -f
    compose.mac.yaml restart --no-deps S`. Anything else: "no conoce esa orden".
  - It answers BEFORE it acts; an answer that cannot be delivered means the order is not run (and its lock is given
    back). A reboot waits 5 s after its "ok", so the api's reboot row lands before the host goes down. The api trusts
    a reboot the butler took (its "ok" or no word) only if the ventanilla ends within 3 minutes: still alive then,
    the warned chats hear that it did not happen (an "ok" says the butler took the order, not that the host rebooted).
  - One order at a time: a line that arrives while one runs is refused ("todavía está con la orden anterior
    (...)"), and the probe still answers. A command still running after 3 minutes is stopped. A command that fails
    after its "ok" shows in the butler's log (`journalctl -u lpq-butler`), not in the room.
  - The lock: reboot and each restart line once per 10 minutes, per full line; scale has none. Its memory is
    /var/lib/lpq-butler/locks.json (root-only), written whole BEFORE the command runs: a line whose lock cannot be
    written is refused; an unreadable file counts as empty (said in the log). The lock is judged on the clock, within
    10 minutes either side of when the line was taken: a clock that jumps back far frees the line instead of locking
    it for the whole jump (a small step back stretches the lock by that step).
  - It does not start (the room shows it red) when docker, systemctl or /opt/lpq_vision/compose.mac.yaml is missing,
    when another butler answers at the mailbox (or cannot be judged), or when something that is not a socket sits
    there; a socket where a connect is refused is a stale one, and is replaced. A stop (systemctl stop, docker stop)
    ends it cleanly and removes its own socket: the folder is left empty.
  - --dry-run: the same answers, lock and one-at-a-time rule, but each command is printed instead of run. The
    laptop's round trip runs it in a throwaway container (lpq-butler-prueba: the fastapi image, no network, the
    mailbox folder mounted; the program copied in with docker cp, the road this ledger already proves for Windows
    paths), then stops it (docker stop) and removes it.
  - The unit: Type=exec, `python3 -I /usr/local/lib/lpq-butler/lpq_butler.py`, Restart=always,
    Before=docker.service; the mailbox folder (RuntimeDirectory, 0700) is kept across the butler's restarts
    (RuntimeDirectoryPreserve: a new folder would hide the socket from fastapi's mount); the lock's folder
    (StateDirectory, 0700); UMask 0077; IPAddressDeny=any (no IP traffic). No other sandboxing: the three verbs need
    root's reach, and only the server can prove a stricter unit.
